# ADR 0003: Python runtime of the guest

[Português](0003-python-runtime.md)

Status: accepted.

## Context

The guest has no Linux, POSIX or CPython. The interpreter needs to run freestanding, with a fixed heap, modules chosen at build time and a collector that knows the live roots in registers and stacks.

## Decision

The runtime is MicroPython 1.29.0, pinned by hash in `toolchain.lock.toml`, with a port of its own in `ports/micropython/`. The upstream `qemu` port is not used: it runs in M-mode with semihosting and does not fit the privilege model of the project.

There are two profiles of the same source lock, without a fork of the interpreter:

- `supervisor`: runs in S-mode inside the kernel image, with a fixed heap of 8 MiB.
- `user`: runs in U-mode as a separate image, with its own heap and stack inside the region of the process.

In both profiles:

- Only modules frozen as bytecode at build time. The compiler and the REPL are off, and `eval`, `exec`, `compile`, `open` and `input` do not exist. ADR 0009 changes this point for the `user` profile, which gains the compiler to execute programs read from the volume; the `supervisor` profile stays without it.
- `MICROPY_ENABLE_EXTERNAL_IMPORT` is on because that import path is the one that resolves frozen modules and packages. Nothing from outside the image is loaded: `mp_import_stat` answers that no path exists, `MICROPY_PERSISTENT_CODE_LOAD` is off and `sys.path` holds only `.frozen`.
- The configuration starts from `MICROPY_CONFIG_ROM_LEVEL_MINIMUM` and enables feature by feature in `ports/micropython/shared/mpconfigshared.h`.
- Long integers use MPZ. Floating point is off.
- NLR uses the native implementation `py/nlrrv64.c`.
- Collection uses `gc_helper_collect_regs_and_stack`, from `shared/runtime/gchelper_native.c`: it reads `s0` to `s11` with `shared/runtime/gchelper_rv64i.s` and scans the stack up to the registered top. Finalizers are off.
- The stack check of the interpreter is on, with a margin of 2048 bytes. Endless recursion ends in `RuntimeError` and the stack stays usable.
- An unhandled exception in the supervisor prints the traceback and ends the boot with a failure.

No hosted libc enters the link. The memory and string functions come from `shared/libc/string0.c` of MicroPython itself, and `libgcc` is the only compiler library. `kernel-tool verify-artifacts` fails if the link map shows another origin.

## Consequences

The guest has no `typing`, `dataclasses`, `enum`, `asyncio` or `struct`. The code in `src/` uses annotations that the MicroPython compiler discards and no CPython import. The accepted differences are in `docs/architecture/runtime-differences.en.md`.

Passing `mypy` does not prove that a module runs in the guest. The proof is the bytecode generated by the pinned `mpy-cross` and the execution on QEMU.

A private runtime per process fits the profile: the `processes` suite keeps 16 processes alive, 15 of them with the maximum heap of 4 MiB, and the frame reserve of the supervisor stays free.

## Assumptions to confirm

- The `user` profile loads programs that are not frozen. What remains to decide is between compiling in the process and loading a validated `.mpy`.
- Floating point enters the `user` profile together with the `lp64d` ABI. The context switch already saves the FP state of each process.
- The pauses of the supervisor GC fit the budget of work between safe points.
